# Module 03 — Operate MCP tools under limited authority

**Serves oracle:** S04, S10, S11, S14, S18, S19  
**Primary objective:** PO-03 — Operate MCP tools under limited authority  
**Prerequisites:** Preflighted accessible environment, this module's supplied case, and the supplied MCP server  
**Consumes:** VERIFY:PREFLIGHT; VERIFY:CASE; VERIFY:MCP_SERVER  
**Produces:** MCP_CONNECTION; HANDLING_REGISTER; AUTHORITY_BOUNDARY; COMPOSED_NEGATIVE; REVOCATION_RESULT; PO03_RESULT  
**Rough time:** about 3 hours  
**Performance stage:** Independent  
**Work surface:** Tool-assisted professional artifact  
**Practical work:** In a supplied Obsidian research vault of forty notes, read the supplied MCP server's contract before connecting it, declare a minimal authority for the research phase and make the server enforce it, and prove the limits with a probe that attempts each forbidden action itself. Decide six notes' handling before any AI proposal, then connect the server, have the AI research the supplied question and propose a handling for every note, and check each proposal against the stated rules. Narrow the connection for a partner phase that reads only the notes you cleared, scan the AI's extract, and then disconnect and show that no tool is offered.  
**Performance evidence:** MCP_CONNECTION: the contract inspection and your account of it, the declared authority and the matching server arguments, and the launcher's frozen record of the connection. HANDLING_REGISTER: six frozen calibration decisions and a forty-note register with the AI's proposal beside your final handling, rule, and reason. AUTHORITY_BOUNDARY: a probe of the unbounded connection that shows breaches and a probe of each bounded phase that holds every forbidden attempt. COMPOSED_NEGATIVE: the research run in which notes addressed to automation could not change a source, plus the partner extract that cites only cleared notes and repeats no fact from a STAFF note. REVOCATION_RESULT: a run with an empty server map in which the model was offered no tool. PO03_RESULT: the verifier's joined result, with a named residual-risk owner.  
**Failure / HOLD:** Hold for a connection entry that starts anything other than the supplied server, a server whose limits differ from the declaration, a live run that precedes its probe, a changed source note or a write outside the declared folder, a note marked less restricted than the rules require, a STAFF note staged for the partner phase, an extract that cites or repeats STAFF content, or a revoked connection that offered a tool.  
**Scope boundary:** Proves one supplied server's limits on one research vault and one set of handling rules; it does not certify real-world classification, make the AI's judgment reliable, or authorize building an MCP server.  
**Handoff:** Give the next owner the finding and what the sources do not support, the authority in force for each phase, what the probes showed, which of the AI's handling proposals you overrode and why, the revocation proof, and the residual-risk owner.

## Why

A connected tool does whatever its server allows, so a harness that trusts the server's own description is only as safe as the server is honest. Operating one safely means reading its contract, limiting what it may reach, and proving the limit; judging the assistant's work on it means checking its classifications against rules rather than accepting them.

## Enabling objectives

1. Inspect an MCP server's contract, including its instructions and each tool's claims, and connect it to the harness with a declared connection.
2. Judge an AI's handling classifications against stated rules, and use the decisions you accept to scope what a later phase may read.
3. Limit a connection's authority at the layers that can enforce it, prove each limit with a model-free probe, and disconnect with proof.

## Check the work

Inspect each claim separately. The **connection** claim shows the contract was read before any live run, the declared authority and the server's arguments agree, and each live run's receipts agree with the server's own log and the files on disk. The **classification** claim shows the six calibration decisions were frozen before the research run, the register records the AI's proposal beside the learner's decision, and no note is marked less restricted than the rules require. The **authority** claim shows the unbounded probe breached, each bounded probe held every forbidden attempt, each probe tested the exact files its run used, and the revoked run was offered no tool. PO03_RESULT records the verifier's joined result; a clean model transcript is not evidence that a limit holds, and a refusal to connect is not evidence that a tool was operated.

## Supplied-case domain (adapter)

Research a supply question in an Obsidian vault through a supplied MCP server, then prepare one extract for a partner liaison cell. The case is Kiln Hold: Task Force Marlin staff at Forward Base Brandt need 40 burn-dressing cases from Mill Depot at Clinic B-2, and the pile holds forty notes, `KH-001` to `KH-040`, with a stock count whose newer report is printed in local time, a lot on hand that is on a quality hold, a deadlined truck, a bridge posted below the truck's class, and an approved flight inside a dust forecast. Seven written handling rules decide each note's effective level among OPEN, PARTNER, and STAFF, and only the Release Authority changes a marking or releases anything. Two notes are addressed to automation. The supplied server offers twelve tools, one of them marked read-only although it changes notes, and its instructions steer the model toward tidying the vault. The learner declares three phases (research, partner, and revoked) and never builds or edits the server. The case is fictional and class-only and does not prefill any declaration, marking, or extract.
