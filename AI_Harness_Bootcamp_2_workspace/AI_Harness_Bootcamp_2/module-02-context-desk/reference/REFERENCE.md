# Staff reference: Module 2 · Build and control a reusable second brain

This active staff reference defines the source-to-vault-to-cold workflow and its semantic review. Keep it outside learner downloads, search, prompts, model read roots, and prepared work copies. Historical evidence and reviews remain unchanged; they describe earlier exercises and do not prove this workflow.

## Capability and boundary

Using verified sources and bounded direction, the learner directs an automatic three-stage run under an explicitly loaded saved rule, inspects the generated versioned Knowledge and Reviews, confirms via run records and fresh retrieve that only the frozen snapshot and rule were used, supplies short feedback, and demonstrates the correction in a subsequent revision and retrieve. The three enabling objectives are source-backed selection/relationships with evidence separated from instructions; inspection of generated content plus saved-rule/load proof via run evidence and retrieve; and one substantive improvement demonstrated by feedback plus a fresh run that cites the focal change.

Source verification and bounded direction are earlier capabilities. Saved instruction files and proof of their load are newly taught here. Do not turn this into hidden-fault diagnosis, person-to-person transfer, code writing, plugin setup, autonomous state maintenance, or a scored qualification exercise.

The supplied forty DN notes, file screen, and shared tool guard remain unchanged. Module 02 asks the shared launcher for `--thinking low` on each phase; the optional flag leaves other callers' thinking behavior unchanged. The pinned provider/model, 300-second per-session deadline, and no-retry policy stay in place. Runtime assets belong to this repository. The original P4 checkout is an authoring source only, never a learner dependency.

## Fixed working contract

The editable Obsidian root is `W/vault`. Original sources live at `W/vault/Sources`. For each run the helper stages a read-only packet under `runs/<rev>/inputs/judge/` (all 40 DN copies + Feedback.md + previous-judgments.json + previous-build.json for v2). The v2 judge stage actually reads the staged prior and Feedback; build receives the validated judgments. Cold read root is `W/cold/<revision>` (contains only MOC.md + Knowledge/<rev>/KB-*.md). `W/shared/controls/SAVED_INSTRUCTION.md` stays outside both roots and is injected explicitly by the launcher before any provider contact. `E` is a fresh sibling of W outside the checkout.

Initialize records the original source and rule identities and seeds the forty source notes under Sources/, empty Knowledge/ and Reviews/ directories, MOC.md, and Feedback.md (short guidance text). One `run --revision v1 --runner ... --evidence E/v1` executes the full automatic judge (claims against all forty under the saved rule from staged packet) + build (notes from validated judgments; MOC title/labels derived by helper from the build notes) + automatic freeze + retrieve. Feedback for correction is a plain Markdown note; a subsequent `run --revision v2 --previous v1 --focus-note KB-XXX --feedback ...` consumes the frozen v1 judgments/build plus the feedback as read-only data in staged packet. Retrieve is part of run and also available as separate fresh process against a specific revision's cold snapshot. Three to five notes is a workload guide, never a checker quota. Top-level malformed output or runtime proof failure is distinguished by the terminal exit.

The helper during `run` writes the versioned vault/Knowledge/<revision>/KB-NNN.md , vault/MOC.md (latest), vault/Reviews/<revision>-judgments.md and -answers.md using the validated judgments. No human prepares, populates, or admits the notes; Drafts, note templates, and manual admission receipts are removed. The learner inspects the generated Knowledge and Reviews in Obsidian, performs nonblocking source check by following the exact DN citations to original Sources, and writes a short plain Feedback.md (source citation + desired correction effect). Feedback is captured by the next run (frozen into packet). No public review or freeze subcommand; freeze is internal to run. The learner does not edit the generated KB bytes for the run.

Each judgment cites exact source excerpts. Its coverage record gives a `source_id` and a short `reason` for each of the forty sources; the helper derives the displayed source-to-claim IDs from validated citations. The model does not generate a second copy of that index. Quote instructions require continuous verbatim spans, not joined sentences or rewritten excerpts.

The judgment prompt explicitly requires JSON newline escapes to preserve source paragraph boundaries: a blank line is `\n\n`, not a space. Separate passages may be separate citation entries with the same source ID. Exact-match validation remains unchanged; this guidance does not authorize whitespace normalization or repair of captured responses. A local DN-038 smoke check rejected the flattened two-sentence quote and accepted both the preserved paragraph span (L10–L12) and the two individual sentences (L10 and L12). This is a quotation-boundary check, not a claim of model reliability.

The generated notes contain a title (H1), then four sections (Claim, Limits and conflicts, Evidence, Related) whose exact headings and H3 evidence formatting are defined by the renderer. Evidence contains ### [[Sources/DN-NNN]] followed by blockquoted excerpts. Knowledge links use versioned vault-relative `Knowledge/<rev>/KB-NNN` paths (rev-qualified accepted for navigation). Source links accept unique `DN-NNN` or `Sources/DN-NNN` identities. Source mode is essential when inspecting meaningful Markdown bytes. Do not teach learners to edit hashes, locators, JSON, YAML, or captured responses.

The generated MOC starts with a `# ` title on its first line, followed by one `- [[Knowledge/<rev>/KB-NNN|label]]` entry per nonblank line. The builder output supplies note_ids, titles, and related; the helper derives the MOC title and the list of links from the build result. No surrounding answer prose, subheading, numbered bullet, or trailing text appears. No completed graph is provided to the learner.

A v2 revision verifies v1 independently of live bytes, requires new/changed Knowledge with the prior frozen state, forbids deletion of earlier Knowledge, and binds a changed/new focus note. MOC and reciprocal links may change. Frozen content for a revision is exactly the cold/<revision> copy of MOC plus the generated Knowledge only. No Reviews (judgments record lives in vault/Reviews/ outside cold), Templates, Drafts, Sources, `.obsidian`, chat, staff material, or raw packets are in cold. The manifest/identity (in identities/<rev>.json) is external, schema version 2 (clean cutover), with sorted entries, root fingerprint, source/rule/prompt identities, judgments/build shas, previous-manifest hash, and focal note. Check compares frozen bytes and immutable identities, not later live Knowledge or editable reason notes. Staged packets under runs/<rev>/inputs/ (judge receives Feedback + prior for v2; build receives validated judgments + prior build for v2).

## Runtime proof and judgment

For each paid phase require the shared audit, `policy.profile == 'read'`, `policy.thinking == 'low'`, `policy.tools == ['course_read']`, exact canonical phase root, actual prompt hash, and non-null saved-rule identity matching initialize and the cold manifest. Instruction-loaded evidence precedes provider contact and matches the rule's loaded text. Require unchanged inputs and empty output hashes. The shared launcher and guard are reused, not reimplemented.

Run phase needs forty distinct executed DN file reads; 39 plus a duplicate is insufficient. Retrieve needs an actual MOC read and actual reads of every cited frozen KB. Successful file reads must be frozen members. A listing is not an evidence read. A later revision must read and cite its focal note. No raw packet, Draft, chat, audit, or staff answer is successfully read. Evidence directories are E/<revision>/{judge,build,retrieve}/.

Call classifications remain observational: EXECUTED; ALLOWED_ABSENT for allowed in-root missing paths with no executed read; DENIED when the guard refuses the call or the runtime rejects an unavailable tool before the guard runs; and NOT_ATTEMPTED when no relevant call exists. A pre-hook denial has a runtime rejection but no guard decision row, and the shared audit must still pass. Raw-source observations inspect path references in all string argument values, including nested objects and arrays; they do not prove a read. An ALLOWED_ABSENT observation alone is not raw access or a helper failure. Preserve errors and any shared-audit failure. Do not claim a live denial without an actual denied call. Existing offline guard tests establish containment; this module adds only the staged packet and automatic continuation.

Missing saved instruction is prerequisite exit 2 before provider contact or evidence creation. For the negative: rename only the work-copy rule, invoke retrieve --revision v1 on the existing v1 (after v1 inspection, before feedback; no --previous or --feedback for this negative) which returns 2 with no evidence or provider contact, then restore identical bytes. The subsequent successful v2 run (which includes its retrieve) serves as the positive demonstration. Re-check v1 after v2 to prove preservation. Never count the synthetic oracle as an observed provider or human run.

For every material statement, check a cited KB actually read and its underlying DN/excerpt. Human source inspection may follow original links outside the cold runtime. A truthful unsupported v1 answer is an audit target, not a runtime failure. All three final answers require source-backed support; a remaining gap requires another substantive reviewed revision and fresh run.

The improvement identifies a gap from the v1 retrieve. The learner supplies concise feedback; the v2 run produces the revised Knowledge and focal note. The helper establishes the input identities from the staged packet and that the v2 retrieve read and cited the focal note; the human judges via source inspection whether the change helps the answers. Cosmetic or unchanged answers are reported honestly. A remaining gap requires another feedback + revision + retrieve.
