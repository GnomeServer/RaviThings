E. WINDOWS-SPECIFIC HAZARDS NOT NAMED.
1. platforms/windows-powershell.md:107 — `[Environment]::SetEnvironmentVariable('Path', ($parts -join ';'), 'User')` rewrites the User PATH as REG_SZ. If the existing User PATH was REG_EXPAND_SZ containing `%USERPROFILE%\...` (common on corporate images with login-script-managed PATHs), the percent-expansion is destroyed and every entry that relied on it stops resolving. This is the classic PATH-corruption footgun and the guide neither warns nor backs the old value up. It also does not warn about the 2047-character User PATH limit that managed images routinely approach.
2. Same block, line 108: the persisted value filters empty elements with `Where-Object { $_ }` but the in-process `$env:Path` assignment does not, so a trailing `;` in the inherited PATH survives into the session as an empty element. Reference A7 forbids exactly this and the two lines of the same block disagree with each other.
3. `Get-ComputerInfo` (windows-powershell.md:17, windows-wsl.md:16) routinely takes 20-60 seconds on PowerShell 5.1 and has known null-index failures on some builds. It is a slow, silent step with no duration annotation — the A9 rule the module applies to every `brew install` and `npm install`.
4. windows-powershell.md:53 installs `OpenJS.NodeJS.LTS` and expects Node 24.x. That id tracks whatever is LTS at install time; when Node 26 goes LTS in the autumn this guide starts failing its own check with no pin to explain it. Four of the other tools carry explicit pins; Node does not.
